## 修改一：二维码内嵌访问密码

**文件**：`lib/service.mjs`

新增 `qrTextFor(base, host)` 函数（位于工厂函数体内、`return {` 之前），
并修改 `status()` 中的二维码文本来源：

```js
// 原版
lanQr:    await qrCached(lanUrl),
tunnelQr: await qrCached(tunnel?.url ?? null),

// 修改后
lanQr:    await qrCached(qrTextFor(lanUrl, lan)),
tunnelQr: await qrCached(qrTextFor(tunnelUrl, tunnelHost)),
```

受密码保护的入口会在二维码里追加 `?token=<PIN>`，使扫码一次直达。
该参数是 proxy 自身支持的通道（`lib/proxy.mjs` 的 `authCheck`），
命中后种下 HttpOnly cookie；随后该 query 会被换成 launch token 走握手，两者不冲突。
局域网未开启密码保护时行为与原版一致。

## 修改三（已取消）：修复公网隧道自动恢复失效

**文件**：`lib/index.js`

```js
// 原版
home: internals.home,

// 修改后
home: internals.home ?? (process.env.DSH_HOME ?? join(homedir(), '.dsh')),
```

生产环境下 DSH 调用 `apply(ctx, config)` 不传第三参数，`internals` 恒为 `{}`，
于是 `home` 恒为 `undefined` → `service.mjs` 中
`autoStatePath = home ? join(...) : null` 得到 `null` →
`persistAutoTunnel()` 与 `restoreTunnelIfNeeded()` 双双成为空操作。
即上游「公网隧道自动恢复」功能实际从未生效：标记文件从不落盘，
DSH 重启后隧道也不会恢复。

## 修改三：Windows 上开启公网不再弹出控制台窗口

**文件**：`lib/tunnel.mjs`（`startNamedTunnel` 与 `startQuickTunnel` 两处 `spawn`）

```js
// 原版
const child = spawn(bin, ['--no-autoupdate', 'tunnel', '--url', `http://127.0.0.1:${port}`, '--protocol', 'http2'], {
  stdio: ['ignore', 'pipe', 'pipe'],
  env: cloudflaredEnv(),
});

// 修改后
const child = spawn(bin, ['--no-autoupdate', 'tunnel', '--url', `http://127.0.0.1:${port}`, '--protocol', 'http2'], {
  stdio: ['ignore', 'pipe', 'pipe'],
  env: cloudflaredEnv(),
  windowsHide: true,
});
```

`cloudflared.exe` 是 **控制台子系统（CUI）** 程序，而 DSH 宿主本身是无控制台的分离进程
（`MainWindowHandle = 0`，不拥有任何窗口）。子进程没有可复用的控制台，Windows 就会为它
**新建一个可见的控制台窗口** —— 这就是点「打开公网」时冒出来的那个黑框（在 Windows 11 上
由 Windows Terminal 承载，标题就是 `cloudflared.exe` 的路径）。

那个窗口不是装饰：它就是这个进程的控制台。**关掉窗口 = 向 cloudflared 发 CTRL_CLOSE**，
隧道进程随即退出，界面报「开启失败：隧道进程退出（code=0）」，二维码域名立刻失效。

补 `windowsHide: true` 后，子进程用隐藏窗口的控制台创建，既不弹窗也不会因为"没人去关它"
而意外终止。该选项只对 Windows 生效，其它平台无副作用；上游 `lib/service.mjs` 的
`execFile` 已经在用 `windowsHide: true`，这里属于同类疏漏。

**实测（本机 Windows 11 / Node 24.17 / cloudflared 2026.9.1）**：

| | 新增可见窗口 | 隧道结果 |
|---|---|---|
| 原版 | 1 个（`CASCADIA_HOSTING_WINDOW_CLASS` + `PseudoConsoleWindow`，标题为 cloudflared.exe 路径） | 可连，但关窗即退出 |
| 加 `windowsHide` | 0 个 | 可连（`Registered tunnel connection`） |

**同一原因导致的另两处闪窗，一并补上**（不弹主界面，只在点「重启」「更新插件」时一闪）：

- `lib/restart.js`：`restartHost()` 里 `spawnFn(process.execPath, ['-e', helperCode(...)], { detached: true, stdio: 'ignore', env })`
  加 `windowsHide: true`。
- `lib/index.js`：`performUpdate()` 里 `spawn('dsh', [...], { ..., shell: true })` 加 `windowsHide: true`
  —— `shell: true` 在 Windows 上会拉起 `cmd.exe`（同样是 CUI 程序）。

## 修改四：DSH 重启后手机端 401 黑屏自愈

**文件**：`lib/proxy.mjs`（`createPocketProxy` 的上游响应回调内）

```js
// 新增分支（位于 `log?.(\`${req.method} ${req.url} -> ${proxyRes.statusCode}\`)` 之后）
if (
  proxyRes.statusCode === 401 &&
  !didInjectToken &&
  launchTok !== '' &&
  req.method === 'GET' &&
  isHtmlRequest(req) &&
  !String(req.url ?? '').includes('dsh-pocket-rehandshake')
) {
  const stale = String(req.headers.cookie ?? '')
    .split(';')
    .map((part) => part.trim().split('=')[0])
    .filter((name) => name.startsWith(DSH_AUTH_COOKIE));
  if (stale.length) {
    proxyRes.resume();
    res.writeHead(302, {
      location: '/?dsh-pocket-auth=1&dsh-pocket-rehandshake=1',
      'set-cookie': stale.map((name) => `${name}=; Path=/; Max-Age=0; SameSite=Lax`),
      'cache-control': 'no-store',
      'x-dsh-pocket-rehandshake': 'stale-cookie',
    });
    res.end();
    return;
  }
}
```

**为什么需要**：`dsh web` 每次启动都会换 launch token，手机 WebView 里那份与之绑定的
`dsh-auth-*` cookie 随之作废。上游代理逻辑是「请求带了 cookie 就不补 token」
（`upstreamPathWithLaunchToken` 第 606 行），于是陈旧 cookie 会让上游直接回
`401 dsh web authentication required`，手机端表现为**一片黑屏**，用户只能清掉 App 数据
（等于清 cookie）才能恢复。

补丁在拿到 401 时判断「是不是带着陈旧 cookie、且这次没注入 token」，是就替用户把那些
cookie 过期掉，并 302 到 `/?dsh-pocket-auth=1`（该参数会强制注入当前 launch token），
重新握手；握手成功后照旧由代理改写成 200 过渡页再回到 `/`。用
`dsh-pocket-rehandshake=1` 标记保证每条链路最多自愈一次，不会来回跳。

## 修改五：手机端 Markdown 表格完整显示

**文件**：`client/mobile/mobile.css.ts`（源）与 `client/client.js`（构建产物，两份内容同步）

```css
  /* 仅作用于手机断点（max-width: 1023px）内的对话区 */
  [data-phase] [class*="_tableScroll_"] {
    overflow-x: auto !important;
    max-width: 100% !important;
    -webkit-overflow-scrolling: touch;
    overscroll-behavior-x: contain;
  }
  [data-phase] [class*="_tableScroll_"] table {
    width: 100% !important;
    max-width: 100% !important;
  }
  [data-phase] [class*="_tableScroll_"] :is(th, td) {
    min-width: 0 !important;
    max-width: none !important;
    overflow-wrap: anywhere;
    word-break: break-word;
  }
```

**为什么需要**：DSH 官方的表格样式有两处会在手机宽度下裁掉内容：

1. 四列以上的表格会带上 `.md-table-wide`，其规则是 `overflow-x: hidden`，**只有
   hover / focus-visible 才切成可滚动**；触屏既没有 hover、也不会先聚焦，于是最右侧
   的列直接被裁掉，也滚不动。
2. 每个 `th`/`td` 都带 `min-width: 100px`，三列就超过 375px 视口，最后一列掉到屏幕外。

补丁保留横向滚动容器作为兜底（列特别多时仍可左右滑动），但让表格宽度收敛到视口内、
单元格允许换行，这样常见的 2～4 列表格在手机上能完整显示。

## 修改六：Tailscale 入口（跨网点对点直连）

**文件**：lib/service.mjs、client/api.js、client/index.jsx、client/client.js、client/pocket-locales.js

- lib/service.mjs：新增 	ailscaleIPv4()，在 status() 里增加 	ailscaleUrl / 	ailscaleQr，
  ntryInfo() 也带上 	ailscaleUrl；
- client/api.js：edactStatus() 白名单补上这两个字段（不然 RPC 会把它们丢掉）；
- client/index.jsx + client/client.js：设置页在「局域网」和「公网」之间多一块
  「Tailscale 直连」卡片（地址 + 带密码的二维码）；
- client/pocket-locales.js：新增 	ailscaleAccess / 	ailscaleP2P / 	ailscaleHint。

**为什么需要**：cloudflared 那条路是「手机 → Cloudflare 边缘 → 回源到电脑」，绕一圈公网，
慢且不稳。Tailscale 是 WireGuard 打洞后两端直连，延迟通常低一个量级；
手机和电脑登录同一账号即可，不需要开公网隧道。

**为什么不影响原有入口**：Tailscale 用的 100.64.0.0/10（RFC 6598 CGNAT）
在 lib/proxy.mjs 的 classifyHost() 里本来就被判成 lan，所以它自动沿用
局域网那套规则（按「局域网访问」开关与密码走，不需要公网密码）。
没装或没登录 Tailscale 时 	ailscaleUrl 为 null，这块卡片不渲染。
